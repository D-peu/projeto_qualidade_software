## Story

**As an** Administrator,
**I want** to register additional rooms in the application,
**so that** rooms beyond the currently available SALA 1 can be persistently managed as resources.

## Acceptance Criteria

1. **Given** an authenticated Administrator, **when** they register a room with a capacity of at least 20, **then** the application persists one new room, returns its generated ID and room data, and initializes its status as `DISPONIVEL`. The client does not supply the ID or status. (RF03, RF02; INV-18, INV-08)
2. **Given** a room was successfully registered, **when** the authenticated room catalog is requested again, **then** the same generated ID, capacity, and `DISPONIVEL` status appear alongside existing rooms. (RF03; INV-18; CP-89 supports the existing catalog representation, not the create operation)
3. **Given** an authenticated user whose profile is not Administrator, **when** they attempt to register a room through the interface or call the underlying operation directly, **then** the operation is denied and no room is created. An unauthenticated request is also rejected without creating a room. (RF02; INV-08)

## Scope

### Included

- An Administrator-only create operation and the corresponding Administrator interface entry point; the only submitted room attribute is capacity.
- Persist a new room using the existing model, then use the existing room catalog read operation to confirm it is visible after creation.
- Enforce the Administrator permission for the room-creation operation.
- Automated and API-level verification of generated identity, persistence/read-back, existing capacity constraints, and denied access.

### Out of scope

- Editing or deactivating rooms.
- Creating or managing teachers, materials, users, blocks, or maintenance periods.
- Room search/filtering, reservation changes, and unrelated administrative features.
- Introducing room names, physical labels, locations, or other room attributes not defined by the current requirements/model.

## Dev Notes

### Requirements and scope

- RF03 permits the Administrator to register, consult, edit, and deactivate rooms, teachers, and materials. This story takes only the room-registration slice; the other operations and resource types remain out of scope. [Source: `docs/prd/requisitos-funcionais.md#2-cadastros-e-disponibilidade`]
- RF02 requires the application to prevent users from performing operations not permitted by their profile. The Administrator persona lists room management as permitted; authorization must apply to the server operation and not only to a hidden/disabled UI control. [Source: `docs/prd/requisitos-funcionais.md#1-autenticacao-e-controle-de-acesso`; `docs/prd/personas/admin-sistema.md#permissoes`]
- The current API lists rooms using `GET /api/salas`; the route has no create operation. The API documentation says administrative room registration is not yet available. [Source: `docs/api-reservas.md#rotas`; `docs/api-reservas.md#integracao-do-frontend`]
- **Generated-ID decision:** use the existing generated `Long id` as the room's persistent identity and catalog identifier. The JPA entity uses `@GeneratedValue(strategy = GenerationType.IDENTITY)`; `SalaResponse` exposes that ID together with capacity and status. This is sufficient to distinguish persisted room records in this feature; no human-readable room number/name or location is specified in the PRD/model. If physical labels are later required, that is a separate PRD/model decision and is not a blocker for this story. [Source: `src/main/java/br/com/projeto_qualidade_software/projeto/entities/Sala.java`; `src/main/java/br/com/projeto_qualidade_software/projeto/api/dto/SalaResponse.java`; `docs/prd/requisitos-funcionais.md#2-cadastros-e-disponibilidade`]
- `Sala` currently requires non-null capacity of at least 20, generates its ID, and initializes `statusSala` to `DISPONIVEL`. The response contains only ID, capacity, and status. Treat capacity as the only creation input; do not infer extra fields or change these model constraints. [Source: `src/main/java/br/com/projeto_qualidade_software/projeto/entities/Sala.java`; `src/main/java/br/com/projeto_qualidade_software/projeto/api/dto/SalaResponse.java`]
- Relevant implementation surfaces are `src/main/java/br/com/projeto_qualidade_software/projeto/api/SalaController.java`, `services/SalaService.java`, `repositories/SalaRepository.java`, and `entities/Sala.java`; the existing room catalog is consumed by the static frontend under `src/main/resources/static/`. Follow the current Spring Boot/session authorization and persistence patterns rather than adding a second implementation path.
- **Dependency:** story 1.2 supplies the current frontend/API integration and authenticated-session behavior, but is `InReview`. Before implementing this story, verify that the target branch retains its session/profile behavior and that its QA gate is cleared; do not implement or modify story 1.2 here.
- **Complexity estimate:** Small-to-medium; one create-only resource operation, its profile gate, interface entry point, persistence/API tests, and contract documentation.
- **Risks:** accidentally accepting client-supplied identity/status; weakening the minimum-capacity validation; checking authorization only in the UI; or treating a generated database ID as a user-facing physical label. Prevent these by API-level tests and the scoped generated-ID decision above.
- No local parent epic or `accumulated-context.md` was found. Related stories 1.1 and 1.2 were checked for coherence; neither is changed by this validation.
